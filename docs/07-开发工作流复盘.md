# 07 · 开发工作流复盘（敏捷开发执行 SOP）

> 来源：dsh-toolbox 从立项（S1）到封板（v0.7.0 · S6-a）的完整过程
> 适用：未来的开发者，或者下一个接手这个项目的 AI
> 读法：**前三节是必须背下来的核心**，后面是具体套路

---

## 一、五条核心原则

### 1. 红灯优先：先证明"会坏"，再证明"修好了"

**不要先写实现。** 顺序永远是：

```
1. 写一个会失败的测试（或者先跑一次，亲眼看到红）
2. 确认它红得"对"（错在预期的地方，不是模块找不到）
3. 再改代码
4. 看到它变绿
5. 再补一条"反向"测试：证明旧代码确实会红
```

本项目最典型的例子：`test/host-adapter.test.mjs` 先写，跑出
`ERR_MODULE_NOT_FOUND: Cannot find module 'dsh-adapter.js'`——
这就是红灯确认，然后才开始写实现。

**为什么这条最重要**：假绿灯比红灯危险。一个从不失败的测试等于没有测试。

### 2. 数据先于推断：报错先查磁盘/运行时，不要猜

遇到"看起来不对"的现象，**第一个动作是查真实状态**，不是改代码。

```sh
# 这个项目的标准三步
node tools/verify-trash.mjs          # 磁盘 + 接口
node tools/scan-undefined.mjs        # 全仓漏导入
node tools/contract-check.mjs        # 官方契约体检
```

**踩过的坑**：S4 时"侧栏残留"排查了三轮都在猜，最后是查
`workspace.json` 的 `tables.workspaces` 才发现——数据层早就干净了，
是页面渲染缓存。

### 3. 每个副作用都要能撤销

一个功能如果"关掉开关后留下痕迹"，那它就是半成品。

```js
mount(ctx, env) {
  const timer = setInterval(...)
  env.track(() => clearInterval(timer))   // 必须能撤
  return () => handle.dispose()           // 或直接返回 disposer
}
```

容器的 `reversible: true` **不是装饰**——它代表"关掉能完全还原"。
声明 `true` 却做不到，就是 S4 那种"删了还残留"的根源。

### 4. 官方接口只经 adapter，缺了只降级

所有对 DSH 官方服务的访问都走 `dsh-adapter.js`：

```js
const dsh = createDshAdapter(ctx)
const sessions = dsh.get('sessions')   // 缺了 → undefined，只警告一次
if (!sessions) return                  // 降级，不抛
```

**判据**：你要的东西缺了，插件应该「少一个功能」还是「整个白屏」？
答案永远是前者的，走 adapter；只有真正装不上的（`slots`）才明确抛错。

### 5. 一次只改一件事，改完立刻验证

**这个项目最大的时间浪费，是"一次改多处 + 替换不命中"**：

- 用 `replace` 改代码，锚点没命中，**静默什么都没做**，你以为改了
- 改完立刻 `node --check` + `grep` 确认，是纪律不是谨慎

```sh
node --check src/xxx.js                     # 语法
grep -n "新代码" src/xxx.js                 # 真的进去了吗
node tools/scan-undefined.mjs               # 忘了 import 吗
```

**这个项目至少有 6 次**因为"替换没命中"而误以为改好了。

## 二、接一个新需求：标准动作

```
① 读需求 → 用一句话复述（复述错了立刻暴露理解偏差）
② 找"这件事的定义在哪" → 查官方接口/现有代码，不猜
③ 写红灯测试
④ 实现最小可用版本
⑤ 跑全量测试（不是只跑新测试）
⑥ 让黑盒测试员真机验证
⑦ 提交 → 记录到简报
```

**第 ② 步的关键**：这个项目里，「未分组」查了三轮才确认它
**不是实体**（= `sessions.list` 减去各工作区成员）。如果一开始就去
查 `workspaceRegistry` 有没有「未分组」这条记录，会浪费一整天。

## 三、接一个新 Bug：标准动作

```
① 先复现（不是先改代码）
② 拿证据：日志 / 磁盘 / 接口 / 截图，至少两样
③ 定位到"哪一层"：数据层？渲染层？时序？
④ 写一条能锁死这个 bug 的测试（会红）
⑤ 改代码 → 测试变绿
⑥ 跑全量 + 真机
```

### 分层判断（这个项目最常用的判据）

| 症状 | 先查哪 | 典型根因 |
|---|---|---|
| 侧栏显示不对 | 磁盘 + 运行时状态 | 渲染缓存 / 没 `sessions.refresh()` |
| 操作报错 | 终端第一屏 | 服务缺失 / 接口改名 |
| 恢复后数据不对 | journal + 目录 | 状态机断层 / 快照丢了 |
| 显示"未命名" | `session_projcache/sessions/<id>.json` | 标题快照被删 |
| 反复刷屏 | `heal` / `sweep` 的触发条件 | 终态被当待办 |

## 四、死胡同止损：怎么判断"该停了"

这个项目遇到两次死胡同，处理方式值得照抄。

### 案例 1：typert（S4c）

**走不通的信号**：TypeScript 的 `@Remote` 装饰器在这个运行时下
编译出来是**空壳**——构建"成功"，但表里没有方法。

**止损判据（三条全中就该停）**：
1. **构建成功但运行时不生效**（假绿灯，最难查）
2. 需要**改运行时/编译选项**才能通（超出插件边界）
3. **已有替代路径**（普通的 `webServer.register` 就能做到）

**动作**：
- 写一份 `S4c-typert死胡同排查报告.md` **记录为什么走不通**（不是悄悄删掉）
- 删掉死代码（`remote.ts` + `typert-build.mjs`）
- **历史价值由报告和 git 历史保留**，不留死代码在工作区

### 案例 2：两阶段删除（S4 的 <1 秒闪现）

**止损判据（收益 vs 代价）**：

| 收益 | 代价 |
|---|---|
| 消除 <1 秒的视觉闪烁 | 新增 1 条路由 + 客户端两次往返 + 一个**新的中间态**（阶段 1 成功、阶段 2 失败） |

**结论**：数据 100% 正确的前提下，**不做**。记录成「已知限制」。

**一句话判据**：
> 用真实的复杂度，换想象出来的完美——不换。

## 五、怎么配合"黑盒测试员"（老板）

他的特点：**不读代码、只看屏幕、会截图、会记住每一个不一致**。

### 你的义务

1. **每次给他操作步骤，必须能"照抄"**
   - ❌ "重启一下" → ✅ "重启 `dsh web`，然后 Ctrl+F5"
   - ❌ "刷新页面" → ✅ "**Ctrl+F5**（硬刷新）。重启 ≠ 刷新"

2. **告诉他"重点看什么"**
   - 不是"你试试"，而是"重点看终端第一行有没有 `自检 missing=[]`"

3. **区分"要重启"和"只要刷新"**
   - 宿主代码 `src/host/` → **重启**
   - 客户端代码 `src/client/` → **Ctrl+F5**
   - 说错这一条，他会白重启一次，然后就开始不信任你

4. **让他给"基线数字"**
   - "现在归档 14 条、回收箱 1 条" → 重启后对比
   - 这比任何日志都直观

5. **他报的现象，先当真的查**
   - 即使你觉得"不可能"，也先查磁盘
   - 这个项目里他报的「恢复后变未命名」「闪现未分组」，**全是真的**

### 危险动作的规矩

- 在让他做**不可逆**的事之前，必须说清楚「备份在哪、怎么回滚」
- 例：卸载独立插件前，备份 `package.json.bak-<日期>` 并告知

## 六、怎么配合"毒舌审查官"（Pi）

他的特点：**只读代码和文档、逐条挑刺、抓住不一致就退回**。

### 对账格式（必须这样回）

```markdown
| # | Pi 指出的问题 | 修法 | 证据 |
|---|---|---|---|
| 1 | selfCheck 假绿 | 改成每次真实探测 | 空 ctx 实测 {"ok":false,...} |
| 2 | applied 数组不安全 | 改 Map + translated 校验 | 4 个重渲染场景测试 |
```

**最关键的是"证据"那一列**——Pi 不看你说了什么，看你**跑出了什么**。
命令输出 > 测试名 > 你的描述。

### 三条铁律

1. **不许删断言来变绿**
   测试红了，要么代码错，要么测试错，**先说清是哪个**。
   这个项目里因为我的实现变化导致 2 条旧断言过时，我是**改了断言并写明原因**，
   不是删掉。

2. **Pi 说"假 X"的时候，先自查**
   - 「假自检」「假一行注册」「假可逆」——这类批评**几乎都是对的**
   - 判据：**它是不是在"看起来做了"和"真的做了"之间的缝里**

3. **做不到的要如实说**
   这个项目里我说过三次「没做」：
   - 真浏览器自动化（后来补了）
   - 存量 25 处收口（明确豁免）
   - 两阶段删除（不做）
   
   **每次说"没做"都附理由和代价**，Pi 反而都接受了。

## 七、提交与发版纪律

### 一个提交 = 一件事

```
fix(s4): 删除后侧栏残留 - 快照 workspaceSeat，用 record.sessionIds 兜底
feat(s5): 插件汉化迁入容器并支持还原
docs(s6): 封板报告 v0.7.0
```

前缀：`feat` / `fix` / `docs` / `chore` / `build`

### 发版前检查清单

```
[ ] npm test 全绿（0 skipped，不许"没环境就跳过"）
[ ] chain: scan-undefined 0 可疑
[ ] chain: contract-check 5/5
[ ] package.json 版本 == package-lock.json 版本
[ ] 所有文档里的版本号一致（README/简报/索引）
[ ] MANIFEST 校验通过（如果做了外部资料库）
[ ] git status 干净
[ ] tag 前让审查官看一眼（不要抢跑）
```

### 版本号纪律（这个项目踩过）

**一个版本号只能有一处真相，其余全是引用**：
`package.json` 是源头，`package-lock.json` 必须跟着，文档里是文字。
三者不一致 = 不合格。

## 八、反模式清单（这个项目踩过的坑）

| # | 反模式 | 后果 | 正确做法 |
|---|---|---|---|
| 1 | 用 `replace` 改代码不验证 | 静默没改，你以为改了 | 改完 `grep` 确认 |
| 2 | 改了源码忘了 `build` | 真机跑的是旧 `client.js` | 提交前 `node tools/build.mjs` |
| 3 | 让用户白重启 | 进程启动时间 < 代码修改时间 | 重启前核对：代码 mtime vs 进程启动时间 |
| 4 | 用"测试绿了"当交付 | 真机还是坏的 | 真机链路 + 工具输出 + 测试，三层互证 |
| 5 | 一次改多处 | 出问题不知道是哪处 | 一次一件，改完立刻验证 |
| 6 | 猜根因 | 排查三轮回到原点 | 先查磁盘/运行时 |
| 7 | 为了消噪音跳过必要重试 | 真需要重试的也被跳掉 | 区分「终态」和「待办」，用 `lastError` 判断 |
| 8 | 新增接口只为修视觉问题 | 引入新失败模式 | 数据正确前提下，视觉边界记成已知限制 |

## 九、给下一个 AI 的交接提示

如果你接手这个项目，先做这三件事：

1. **读 `docs/S6-封板报告.md`** —— 当前状态、已知限制、豁免清单
2. **跑 `node tools/contract-check.mjs`** —— DSH 升级后官方接口还在不在
3. **读 `docs/S5-新功能接入规范.md`** —— 加新功能的唯一标准

然后：

- **不要**改 `index.js` / `container.js` / `registry.js` 来加功能
- **不要**直接读 `ctx.<官方服务>`，走 adapter
- **不要**在没写红灯测试的情况下改核心状态机
- **不要**把「已知限制」当成「待修 bug」（它们是评估过的不做）

## 十、一句话

> **先证明会坏，再证明修好；先查数据，再改代码；一次只改一件事，改完立刻验证；
> 做不到的如实说，做不到的代价算清楚。**
>
> 这套流程在这个项目上跑通了 6 个阶段、448 项测试、5 次封板审核，
> 没有一次是靠"看起来没问题"过关的。
