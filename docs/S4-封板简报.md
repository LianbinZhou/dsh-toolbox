## 二、本轮修掉的 5 个真实缺陷

前四个是**同一个症状**（删除永远 500、侧栏不消失、终端刷屏）的不同层，必须一起修才通。

### D1 · 路由层把异常吞成一句废话（最外层）

`route-guard.js` 删除路由的兜底：

```js
.catch(() => { respond(res, 500, { ok: false, error: 'delete failed' }) })
```

`catch` 连 `error` 都没有，前端永远只看到 `delete failed`，终端一片安静。**这是所有排查被拖长的根因。**
→ 已接住 `error` 并 `console.error` 打完整堆栈；响应体继续脱敏（不外泄路径）。
→ `index.js` 里 `api.delete` 那条 `.catch(() => {})` 同样补上。

### D2 · 中间层吞掉 `seat` 参数（快照法失效的直接原因）

`service-deps.js`：

```js
dropWorkspaceRows: (id) => adapter.dropWorkspaceRows?.(id)   // seat 丢了
```

删除前记下的工作区快照（`workspaceSeat`）根本到不了底层，adapter 只能回头读
`entity.sessionIds` —— 而归档会话的目录已不在原位，这个过滤 getter 既可能返空也可能抛。
→ 改为 `(id, seat) => adapter.dropWorkspaceRows?.(id, seat)`，匹配优先用 `seat.workspaceId`。

### D3 · 把 private 方法当入场券 + 调 private API

- `dropWorkspaceRows` / `reattach` 的入口是 `typeof entity.mutate !== 'function' → continue`，
  而 `mutate` 在 DSH 的 `dsh-workspace` 里是 **private**（`entity.d.ts:87`）。用它当门槛，
  会把"有公开方法、没有私有方法"的实体整个跳过，等于什么都不做。
- 真正的移除/挂回应该走公开方法：**`detachSession` / `attachSession` / `insertSessionBefore`**
  （`entity.d.ts:71-73`，均幂等）。
→ 移除改走 `entity.detachSession(id)`；恢复优先 `insertSessionBefore`（放回原位），
其次 `attachSession`，`mutate` 只兜底。入口门槛改为"有公开方法或私有方法即可处理"。

### D4 · 漏导入 `canonicalSessionId`（真机 500 的直接抛点）

`session-adapter.js` 导入了 `dshHome, sessionsRootFor`，**漏了 `canonicalSessionId`**，
而文件里用了 8 处（定义/导出在 `paths.js:48/234`）。
→ 一进 `snapshotWorkspace` 第一行就 `ReferenceError`，冒到路由层被 D1 吞成 `delete failed`。
→ 已补导入。

### D5 · 状态机谎报 `cleaned` + `heal()` 复读

`finishInner` 在清理失败时返回 `cleanup-pending` 但**沿用旧 phase**，历史条目早已被标成
`cleaned`；`heal()` 每次启动都会重跑同一批必然失败的清理，终端成复读机。
→ 失败时写回 `phase: 'trashed'` + `lastError` + `cleanupAttempts`；
→ `heal()` 对 `cleanupAttempts >= 3` 的条目**跳过**（记 pending，不再刷屏）；
→ 用户手动「彻底删除」仍会再试一次。

## 三、附带修的工具缺陷

**`tools/verify-trash.mjs` 之前会报假绿**：它读 `workspace.workspaces`，
而真实结构是 `workspace.tables.workspaces`（顶层 `unit/global/tables`，已实测确认）。
另外 id 没做 `session-` 前缀规范化比较。
→ 已改正层级 + 规范化比较 + 直接把带 `lastError` 的条目标出来 + 提示"磁盘落盘有延迟"。

**新增 `tools/scan-undefined.mjs`**：跨文件符号比对，专抓"用了别的文件的导出名却没导入"。
判定逻辑 = 本文件既没导入也没声明 ∧ 以调用形态出现 ∧ 别的文件 export 过该名（最后一条压掉注释/CSS 噪声）。
**当前全仓扫描结果：0 可疑**（即只有 D4 那一处，已修）。有可疑时退出码 1，可挂 CI。

## 五、已知边界（不是缺陷，S5 不必回炉）

1. **历史条目没有 `workspaceSeat`**：本轮修复只对新删除生效。之前那批「删除成功但清理失败」
   的条目恢复时可能落「未分组」——用户实测第 2/4 条就是这种情况，属预期。
2. **`heal()` 有重试上限**：连续失败 3 次后不再自动重试，需要手动「彻底删除」推一次。
   这是有意为之（避免复读机），代价是失败会静默停在 `trashed`。
3. **验证工具读磁盘，侧栏读运行时**：`workspace.json` 落盘有延迟，刚删完立刻查可能假绿（已在输出里提示）。
4. **回收箱保留期**：默认 7 天，到期由清理器物理清空；被保护条目（`trashed`/`cleaned`）不会因容量压力被赶走。
