## 0. 一句话

这不是“侧栏缓存没刷新”，也不是归档标记没清。

**目录已经进了回收箱，归档标记也已经清掉；但这条会话还留在 `workspace.json` 的 `sessionIds` 里。**

于是：

- 左侧工作区从 workspace 成员里读到它 → 显示；
- 回收箱从 journal 里读到它 → 也显示；
- 归档标记已经清掉，所以侧栏不再隐藏它。

## 2. 为什么 workspace 行没有删掉

### 2.1 关键代码

`src/host/features/archive/session-adapter.js` 的 `dropWorkspaceRows()`：

```js
for (const entity of entities) {
  const ids = Array.isArray(entity.sessionIds) ? entity.sessionIds : []
  const matched = ids.some(...)
  if (!matched) continue
  await entity.mutate(...)
}
```

它是在**目录已经移进回收箱之后**调用的。

而 `WorkspaceEntity.sessionIds` 是一个 **filtered getter**：

```js
get sessionIds() {
  return this.record.sessionIds.filter(id =>
    this.host.candidateMatches(id, this.record.path)
  )
}
```

目录已经不在原位置后，这个 getter 可能就不再返回目标 id，于是：

```text
matched = false
→ 不执行 mutate
→ workspace 行保留
```

### 2.2 原本应该先快照，但快照没有接上

`session-adapter.js` 里已经有：

```js
snapshotWorkspace(id)
reattach(snapshot)
```

`service.js` 的 `restoreLocked()` 也读了：

```js
if (entry.workspaceSeat && typeof deps.reattach === 'function') ...
```

但全仓库搜索只有这两处引用 `workspaceSeat`：

```text
src/host/features/archive/service.js:466
src/host/features/archive/service.js:467
```

**没有任何地方把 `workspaceSeat` 写进 journal claim。**

也就是说：

- 删除前没有调用 `snapshotWorkspace()`；
- journal 里没有 `workspaceSeat`；
- 恢复时 `reattach()` 永远不会执行；
- `dropWorkspaceRows()` 只能靠移动后已经不可靠的 `entity.sessionIds` 去找行。

这是本轮“快照/恢复”没有真正落地的核心缺口。

### 2.3 失败被吞掉，日志只留一个词

`cleanup()` 里：

```js
try {
  await deps.dropWorkspaceRows(id)
} catch (error) {
  failed.push('workspace')
}
```

没有记录 `error.message`、workspace id、session id 或堆栈。

当前 `.err` 里已经能看到大量：

```text
[dsh-toolbox] cleanup 未完成: workspace
```

这说明 workspace 这一步确实失败了，但日志没有告诉 Harness 失败在哪一条 entity、哪个异常。

`dropWorkspaceRows()` 内部又对 `entity.mutate` 做了空 `catch`：

```js
try {
  await entity.mutate(...)
  dropped += 1
} catch (error) {
  // 行是展示层：失败不该让删除回滚
}
```

所以即使 `mutate` 失败，也没有任何可诊断信息。

### 2.4 为什么 journal 仍然是 cleaned

`heal()` 会遍历所有非 `done` 的 entry，包括 `cleaned`，再调 `finish()`。

`finishInner()` 在 cleanup 失败时只返回：

```js
return { ok: true, removedDir: true, reason: 'cleanup-pending', warning: 'deleted with warnings' }
```

**没有把 phase 改回 `trashed`，也没有写 `lastError`。**

所以：

- journal 继续显示 `cleaned`；
- 每次 `list()` / `heal()` 都重试；
- 每次 workspace 都失败；
- `.err` 里重复出现 `cleanup 未完成: workspace`；
- Harness 看到 `cleaned`，以为删除完成。

这就是“定位不到根源”的第二个原因。

## 3. 为什么 `verify-trash.mjs` 说“没有残留”

`tools/verify-trash.mjs` 里读的是：

```js
for (const [key, entity] of Object.entries(workspace.workspaces ?? {})) {
```

但实际 `workspace.json` 的结构是：

```json
{
  "tables": {
    "workspaces": {
      "...": { "sessionIds": [...] }
    }
  },
  "global": { ... }
}
```

正确的路径是：

```js
workspace.tables.workspaces
```

因为读错了层级，`workspaceRows` 永远是空数组，所以脚本第 2 条证据永远输出：

```text
✔ 没有残留（侧栏不会再显示它们）
```

**这是假阴性。**  
Harness 用它自查，当然定位不到这个残留。

同时脚本用 `entry.keptDays ?? 7`，但 journal entry 里并没有 `keptDays`，所以它显示“剩余≈7 天”，而接口返回的是 14 天；这是次要问题。

## 4. 彻底修复方案

不要选 A/B。正确做法是 **快照 → detach → 恢复时 reattach**。

### 4.1 删除前快照

在 `deleteSession()` 里，移动目录前：

```js
const workspaceSeat = deps.snapshotWorkspace(id)
```

写进 claim：

```js
const claim = {
  ...,
  ...(workspaceSeat ? { workspaceSeat } : {}),
}
```

`snapshotWorkspace()` 必须在目录还存在的**移动前**调用，不能等 `dropWorkspaceRows()` 时再查 filtered getter。

### 4.2 用快照 detach

`dropWorkspaceRows(id, seat)` 不再遍历 `entity.sessionIds` 找目标，而是用：

```text
seat.workspaceId
seat.sessionId
```

直接找对应 entity，执行 `entity.mutate` / `detachSession`，并：

- `await` 完成；
- 返回 `{ ok, dropped, reason }`；
- 失败时记录具体 entity id 和 error.message；
- `dropped === 0` 不能静默成功。

### 4.3 cleanup 失败必须反映到 journal

如果 workspace/cache 失败：

- phase 改回 `trashed`（或专门的 `cleanup-pending`）；
- 写 `lastError`：`workspace: <entity> <message>`；
- 不要继续显示 `cleaned`；
- `heal()` 才能明确知道还欠什么。

### 4.4 恢复时 reattach

`restoreLocked()` 已经有 `workspaceSeat` 分支，补上 claim 后就会执行：

```js
await deps.reattach(entry.workspaceSeat)
```

`reattach()` 用 `workspaceId + sessionId + beforeSessionId` 放回原工作区/原位置。

### 4.5 修 `verify-trash.mjs`

```js
const workspaces = workspace.tables?.workspaces ?? {}
for (const [key, entity] of Object.entries(workspaces)) { ... }
```

并检查：

- workspace 成员；
- `session_projcache.json` 的 `tables.sessions`；
- 每会话缓存文件；
- journal 剩余时间用当前配置/`expiresAt`，不要用 `entry.keptDays ?? 7`。

## 5. 还需要顺手修的两条（同一类问题）

### 5.1 `purge()` 当前没有 cleanup

当前 `purge()` 仍然：

```js
removeTree(entry.trashPath)
journal.update(remove entry)
```

没有清归档标记、workspace 行、缓存。  
如果对 `trashed` 记录点“彻底删除”，文件没了，workspace 行/归档标记仍可能留下。

要求：purge 前先 cleanup；cleanup 失败则拒绝，保留记录。

### 5.2 `unarchiveSession()` 仍没有 await、只清一个拼写

当前恢复路径：

```js
deps.unarchive(id)
```

不是 `await`，也没有遍历 `spellings(id)`。  
归档集合里如果是 bare / `session-` 另一种拼写，恢复后仍可能残留。

要求：复用 `clearArchiveMarkers(id)`，遍历双拼写并 await。

## 7. 结论

这条会话不是“短暂残影”，是 **workspace 行真实残留**。

根因链：

```text
删除时目录移入回收箱
→ cleanup 里 dropWorkspaceRows 失败
→ workspace.sessionIds 保留 id
→ 归档标记又已清掉
→ 左侧工作区显示 + 回收箱显示
→ heal 反复 cleanup 失败，但 phase 仍是 cleaned
→ verify-trash.mjs 读错 workspace.tables 层级，假报“没有残留”
```

先修 `workspaceSeat` 快照/写入、`dropWorkspaceRows` 用快照、cleanup 失败写回 phase/lastError，再修 `verify-trash.mjs`，这条才能闭环。
