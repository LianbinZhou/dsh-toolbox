# S4 封板简报 · 历史归档（archive）

> 状态：**真机验收通过，正式封板**（v0.4.0）
> 日期：2026-10-18 ｜ 测试：**410 / 410，0 跳过** ｜ 运行时：DSH `0.2.1-rc.2`
> 范围：`dsh-toolbox` 的 `archivePanel` + `archiveHttpApi`

## 一、结论

四条主链路 + 两条幽灵链路在真机上全部走通，状态机没有断层：

```
Active ──归档──> Archived ──删除──> Trashed ──到期/彻底删除──> Purged
                    ↑                  │
                    └──── 恢复 ────────┘
                         │
              目录不存在 → dir-absent（清标记，绝不造行）
```

| # | 链路 | 结果 |
|---|---|---|
| 1 | 工作区 → 归档 → 删除 → 回收站 | ✅ 侧栏当场消失 |
| 2 | 工作区 → 归档 → 恢复 → 工作区 | ✅ 回原位 |
| 3 | 归档 → 删除 → 回收站 → 恢复 | ✅ 回到原工作区**原位置** |
| 4 | 归档 → 删除 → 回收站 → 彻底删除 | ✅ 零残留 |
| 5 | 未分组 → 归档 → 删除 | ✅ 不再判失败、侧栏消失 |
| 6 | 归档 → 手动删目录 → 恢复 | ✅ 报 `dir-absent`，不造分身 |

---

## 二、四条不变量（每次操作后都必须成立）

1. **同一会话不能同时出现在回收箱和侧栏**——靠「清标记 + 摘工作区行 + 刷新 Session 列表」三者配合。
2. **`dir-absent` 时不造行**：目录不存在还去恢复/取消归档，只清残留标记并报错。
3. **`purge` 前必须先 cleanup**：清不掉就拒绝，宁可留着也不留幽灵。
4. **恢复要回原位置**：删除前快照 `workspaceId / sessionId / beforeSessionId`。

## 三、本轮修掉的 10 个真实缺陷

### D1 · 路由层把异常吞成一句废话（最外层）

`.catch(() => respond(500, { error: 'delete failed' }))` —— 连 `error` 都没接，终端一片安静。
**这是所有排查被拖长的根因。** → 已接住 `error` 并打完整堆栈，响应体继续脱敏。

### D2 · 中间层吞掉 `seat` 参数（快照法失效的直接原因）

`dropWorkspaceRows: (id) => adapter.dropWorkspaceRows?.(id)` —— `seat` 丢了，adapter 只能回头读
`entity.sessionIds`，而那是 **filtered getter**（目录移走后会藏行）。→ 透传 `seat`，匹配优先用 `seat.workspaceId`。

### D3 · 把 private 方法当入场券

`typeof entity.mutate !== 'function' → continue`，而 `mutate` 是 private。
→ 改走公开方法 `detachSession` / `attachSession` / `insertSessionBefore`（均幂等）。

### D4 · 漏导入 `canonicalSessionId`

一进 `snapshotWorkspace` 第一行就 `ReferenceError`，冒到路由层被 D1 吞成 `delete failed`。→ 已补。

### D5 · 状态机谎报 `cleaned`

`finishInner` 清理失败时返回 `cleanup-pending` 但沿用旧 phase，`heal()` 每次启动重跑同一批必然失败的清理。
→ 失败写回 `phase: 'trashed'` + `lastError` + `cleanupAttempts`，超过 3 次不再刷屏。

### D6 · 未分组会话被判成失败（真机「侧栏永远不消失」）

「未分组」不属于任何 workspace 实体，`dropWorkspaceRows` 返回 `not-found` → cleanup 判失败 → 停在 `trashed`。
→ 改成 `{ ok: true, dropped: 0, already: true, reason: 'ungrouped' }`：**没有行可摘 = 本来就干净**。

### D7 · 没刷新 DSH 的 Session 列表

「未分组」= `sessions.list` 减去各工作区成员。删目录只改磁盘，Session 列表还是旧快照。
→ 客户端注入 `sessions`，动作完成后统一 `sessions.refresh()`。

### D8 · `running=false` 仍报「正在使用中」

`isLive` 用 `sessions.get(id)` 存在当活——那只代表会话加载过（打开过/恢复过）。
→ 改看真实标志：`running / isRunning / status / state`，真在跑才拒绝。

### D9 · 保留天数改了不生效

`index.js` 传 `trashKeptDays`，`service-deps` 读 `ttlDays`，名字对不上 → 静默回落 7。
→ 参数名对齐 + 每次现读配置。

### D10 · `findEntry` 精确比较多拼写找不到

journal 里存的拼写与请求不一致时会直接返回，phase 停在 `trashed`。→ 改 canonical 比较。

## 五、已知限制（Known Limitation）

### 1. 删除瞬间「未分组」闪现不到 1 秒

**现象**：点「入回收箱」的一瞬间，左侧「未分组」短暂出现这条会话，随即消失。

**原因**：删除分三步——移目录 → 清「已归档」标记 → 返回响应 → 客户端刷新会话列表。
第 2 步一发生，DSH 立刻按「未归档」重新分组，而列表要到第 4 步才刷新。

**数据安全**：100% 安全。目录已在回收箱、journal 正常、归档集合已清，只是渲染层重算了一次。

**为什么不在 S4 修**：彻底消除需要「两阶段删除」（先移目录并刷新，再单独调一次清标记），
意味着新增一条路由 + 两次往返。为一个 <1 秒的视觉边界在封板前改删除主链路，风险大于收益。
留到 S5 或专门一轮处理。

### 2. 历史条目没有 `workspaceSeat`

本轮修复只对**新删除**生效。之前那批「删除成功但清理失败」的条目恢复时可能落「未分组」，属预期。

### 3. `heal()` 有重试上限

连续失败 3 次后不再自动重试，需要手动「彻底删除」推一次。这是有意的（避免终端复读机）。

### 4. 验证工具读磁盘，侧栏读运行时

`workspace.json` 落盘有延迟，刚删完立刻查可能看到「没有残留」其实只是还没写下去（输出里已提示）。

### 5. 回收箱保留期

默认 7 天，可选 3/7/14/30/60，范围 1–90；到期由清理器物理清空（启动一次 + 每小时一次）。
被保护条目（`trashed`/`cleaned`）不会因容量压力被赶走。

## 六、安全边界

- 7 条 HTTP 路由，全部要求**进程内令牌** + **Host 白名单** + **同源**；
- 响应只回白名单字段，**不含绝对路径、nonce、异常原文**；
- `archiveHttpApi` **默认关闭**，关闭时同时作废旧令牌；
- 路径校验走**真实 `realpath` + 拒绝 junction/symlink**；
- 原因码单一来源：`src/shared/reasons.js`（内部码 → 出网码 → 中文）。
