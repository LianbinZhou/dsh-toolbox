### P0-2：`/restore` 没有补清归档标记

4.4 的修复在 `unarchiveSession()` 里：

```js
const moved = await restoreLocked(id)
...
```

但新回收箱 UI 调用的是：


`restore()` / `restoreLocked()` 只把文件搬回原位，**没有补清归档标记**。`service-deps.js` 里明确是：

```js
restore: (id) => service.restore(id),
```

### P1-1：`cleanup-pending` 警告在回收箱接口里被丢掉

`trashCommon()` 返回的字段只有：

```text
ok / rows / protectedCount / keptDays / maxProtected / reason
```

没有 `warning`。

但 `archive-client.restoreFromTrash()` 读的是：

```js
warning: body?.warning
```

`service.restore()` 返回的 `warning: 'cleanup-pending'` 到不了前端，UI 不会提示“归档标记没清掉”。

### P1-2：`unarchiveSession` 只清一个拼写

4.4 补清标记用的是：

```js
deps.unarchive(id)
```

如果归档集合里存的是另一种拼写（`session-xxx` 与 `xxx`），只清当前 id 会留下另一个标记。`cleanup(id)` 已经会遍历所有拼写，恢复路径应该复用它，而不是只调一次 `deps.unarchive(id)`。

### P1-3：“真实边界”仍是词法边界

`service-deps.js` 的 `isInsideSessions` / `isInsideTrash` 用的是 `paths.js` 的 `isInside()`，它只做：

```js
resolve(root)
resolve(child)
childAbs.startsWith(rootAbs + sep)
```

这是**词法边界**，不是 `realpath`。一条位于 sessions 根内、但中间经过 junction/symlink 的路径，仍可能被放行。

测试里的 `isInsideSessions` / `isInsideTrash` 也是手写 `startsWith`，所以这批测试证明的是“字符串没穿出去”，不是“真实文件系统没穿出去”。提交说明里的“真实边界”说得过头了。
