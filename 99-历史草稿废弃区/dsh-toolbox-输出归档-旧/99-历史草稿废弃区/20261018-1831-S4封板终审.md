## 2. 阻断封板的代码问题

### P0-1：`dropWorkspaceRows` 仍可能“报成功但没摘掉”

当前返回：

```js
return { ok: true, dropped }
```

`cleanup` 只检查：

```js
if (result && result.ok === false) failed.push('workspace:' + result.reason)
```

所以下面这种情况会被当成成功：

```text
dropWorkspaceRows(id, { workspaceId: 'wrong' })
→ { ok: true, dropped: 0 }
→ cleanup 不报错
→ finish 标 cleaned
→ workspace 行还在
```

我实跑确认：

```text
{ ok: true, dropped: 0 }
record 仍然是 [ session-aaaaaaaa-... ]
```

**这等于把上一轮的侧栏残留原样保留下来，只是多了一个 dropped 计数。**

要求：

- 有 `seat` 但 `dropped === 0` → `ok:false`；
- 没有 `seat`、也完全没匹配到任何行 → 至少返回明确的 `not-found`，由 cleanup 决定是否允许；
- `cleanup` 对 `ok:false` 和 `dropped===0` 都必须算失败；
- 补一条“seat 指向不存在的 workspace”的回归测试。

### P0-2：`detachSession` 用了请求 id，不是快照里的真实拼写

`snapshotWorkspace` 已经记录了真实拼写：

```js
seat.sessionId = 'aaaaaaaa-1111-...'   // 可能是 bare
```

但 `dropWorkspaceRows` 实际调用：

```js
await entity.detachSession(String(id))   // 用的是 session-aaaaaaaa-...
```

`detachSession` 是精确匹配的公开方法；bare / `session-` 拼写不一致时它会幂等返回，但什么都没删。

我实跑：

```text
seat.sessionId = 'aaaaaaaa-1111-...'
entity.record.sessionIds 仍为 [ 'aaaaaaaa-1111-...' ]
dropWorkspaceRows → { ok: true, dropped: 1 }
```

**报 dropped=1，行还在。**  
这和“大小写/前缀拼写”是同一类坑。

要求：

- `detachSession` 必须传 `seat.sessionId`（快照里的真实值）；
- 没有 seat 的旧条目，必须从 `ids` 中找到实际值再传；
- `dropped` 必须表示“真的从 record 里消失了”，不能只看方法没抛；
- 补 bare / `session-` 双拼写回归。

## 3. 恢复路径的两个问题

### P1-1：`reattach` 顺序错了，回不到原位置

当前：

```js
if (canInsert && before !== null) {
  await entity.insertSessionBefore(snapshot.sessionId, before)
}
if (canAttach) await entity.attachSession(snapshot.sessionId)
```

但 `insertSessionBefore` 要求会话已经在 record 里；删除时已经 detach，所以第一次必然失败：

```text
insertSessionBefore -> Error: not accounted
→ 回退 attachSession
→ 会话被插到列表最前面
→ 原位置丢失
```

我实跑得到 `mode: 'attach'`，record 从：

```text
[B]
```

变成：

```text
[A, B]
```

而不是原来的位置。

要求：

1. 先 `attachSession(sessionId)`；
2. 再 `insertSessionBefore(sessionId, beforeSessionId)` 调整位置；
3. 或者直接用一次 `mutate` 在正确下标插入；
4. 补“删除中间项 → 恢复 → 顺序不变”的测试。

### P1-2：普通归档恢复没有 `await`

`unarchiveSession` 的“非回收箱”分支仍是：

```js
if (!deps.readArchived().includes(id)) ...
deps.unarchive(id)
return { ok: true }
```

官方 `registry.unarchiveSession()` 返回 Promise，这里没有 await。我实跑：

```text
unarchiveSession 返回 ok:true 时：
  unarchiveDone = false
  archived = true
稍后才变成 false
```

这会让“历史归档页 → 恢复”返回后侧栏/归档状态短暂不一致。

要求：

- 普通分支也复用 `clearArchiveMarkers(id)`；
- 遍历双拼写并 `await`；
- 补延迟 promise 的回归测试。
