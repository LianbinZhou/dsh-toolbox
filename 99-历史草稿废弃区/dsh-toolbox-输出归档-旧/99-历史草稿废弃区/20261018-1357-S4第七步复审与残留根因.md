## 1. 侧栏残留的根因（已确认）

### 1.1 我在当前 profile 观察到的数据

据我此刻读取 `~/.dsh/storages/workspace.json`：

```text
archive-journal 里 cleaned 记录：8 条
workspace「DeepSeek_Harness_Projects」的 sessionIds 仍包含 2 条：
  session-62eee524…
  session-e637eb69…
```

这两条在 journal 里已经是 `cleaned`，但仍在 workspace 的 `sessionIds` 里。

这与用户看到的现象一致：

```text
删除后侧栏短暂残留 → 重启后消失
```

重启时 DSH 重新索引，目录已经不在 sessions 树里，才把行丢掉。

### 1.2 代码层面的两个空实现

`src/host/features/archive/session-adapter.js` 里：

```js
dropWorkspaceRows: () => {},
scrubCache: () => {},
```

也就是说：

- `cleanup()` 调了 `dropWorkspaceRows`，实际什么都不做；
- `scrubCache` 也什么都不做；
- 旧的 `dsh-archive-manager` 是明确实现了这两步的，见：
  - `dsh-archive-manager/src/host/index.js` 的 `_dropWorkspaceRows()`
  - `dsh-archive-manager/src/host/paths.js` 的 `scrubProjcache()`

### 1.3 `cleanup()` 没有 await

`service.js` 当前是：

```js
function cleanup(id) {
  ...
  deps.unarchive(spelling)       // 官方 registry 返回 Promise
  deps.dropWorkspaceRows(id)     // 可能是 async
  deps.scrubCache(id)
  return failed
}
```

`unarchiveSession` 里也有：

```js
deps.unarchive(id)
```

这些返回值都被丢掉了。

后果：

- `finish()` 可能在归档标记真正落盘前就返回；
- workspace 行移除、缓存清理可能在 HTTP 响应之后才完成，甚至没完成；
- 用户看到的就是“删除成功，但侧栏还在”。

这不是 UI 刷新问题，不能靠 A/B 方案遮住。

## 2. 为什么 A / B 都不选

### A. 保持现状

用户会持续看到已删除会话的残影，直到重启；不可接受。

### B. 删除时不清归档标记，靠列表过滤

- 官方归档集合仍指向一个已经不在 `sessions` 目录里的会话；
- DSH 的其他归档消费者仍可能探测/报“归档目录不存在”；
- 恢复时还要处理“归档标记 + 回收箱”双状态；
- 只是把残留从侧栏挪到归档列表，不是修复。

### C. 推荐：删除时做完整的四步，恢复时重建工作区成员

这才叫彻底修复：

1. **移动前**：记录这条会话在 workspace 里的成员身份：
   - `workspaceId`
   - 实际存储的 `sessionId` 拼写
   - 它前面的 `beforeSessionId`（用于恢复顺序）
2. **移动进回收箱后**：
   - `await` 清归档标记（两种拼写）；
   - `await entity.detachSession(actualId)`，把行从 workspace 移除；
   - `await` 清 projection cache；
   - 全部成功后才把 journal 标成 `cleaned`。
3. **从回收箱恢复时**：
   - 把目录搬回原位；
   - `await` 清归档标记；
   - 按 journal 里记录的 `workspaceId` / `beforeSessionId` 重新 `attachSession()` + `insertSessionBefore()`；
   - 这样侧栏立刻回到原工作区，而不是变成“无分组”。
4. **彻底删除时**：
   - 先完成 cleanup（清标记、workspace 行、缓存）；
   - 再物理删除；
   - cleanup 失败就拒绝/保留，不能先删文件再留幽灵。

如果只做 `detachSession` 而不做恢复时重建，用户从回收箱恢复后会丢失原工作区归属；所以必须把成员身份一起存进 journal。

## 3. 还有一条会留幽灵的路径：`purge()` 不 cleanup

当前 `purge()`：

```js
removeTree(entry.trashPath)
journal.update(remove entry)
```

没有补清归档标记、workspace 行、缓存。

我实跑复现：

```text
delete -> phase trashed, archived true
purge -> ok:true, purged:true
after -> archived true, journal []
```

文件被物理清掉，归档集合还在。

`trash` UI 允许对 `trashed` 记录点“彻底删除”，所以这条路径用户可以直接触发。

修复要求：

- `trashed` 记录 purge 前先执行 cleanup；
- cleanup 失败则拒绝 purge，保留记录；
- `cleaned` 记录可以 purge，但仍要幂等清理；
- 加“trashed + purge 后 archived 必须为 false”的测试。

## 4. 双拼写与 warning 的遗漏

### 4.1 `unarchiveSession()` 仍只清一个拼写

当前代码：

```js
const stillArchived = deps.readArchived().some(...)
if (stillArchived) {
  deps.unarchive(id)
}
```

只传当前 `id`，不是所有拼写。归档集合里如果存的是另一种拼写，仍会留下标记。

我实跑：

```text
archived = ['aaaaaaaa-...-4444']（裸 id）
restore canonical id -> ok:true
after -> archived 仍包含裸 id
```

`cleanup(id)` 会用 `spellings(id)` 遍历，但恢复路径没有复用。

要求：

- 抽一个 `clearArchiveMarkers(id)`：遍历 `spellings(id)`，`await deps.unarchive`；
- `cleanup` 和 `unarchiveSession` 都用它；
- 测试覆盖 bare / `session-` 双拼写。

### 4.2 warning 被刷新覆盖

`archive-panel-model.js` 的 `restoreTrash`：

```js
message = result.warning === 'cleanup-pending' ? phrase('cleanup-pending') : ''
await this.refreshTrash()
```

`refreshTrash()` 成功时会把 `message` 置空，警告立刻消失。

要求：

- 先刷新列表，再设置 warning；或让 `refreshTrash` 保留外部 warning；
- 加测试：`restore` 返回 `warning:'cleanup-pending'` 时 UI 仍能看到提示。

## 5. 保留天数功能：能用，但显示和清理时机不对

### 5.1 配置确实生效

当前 `/trash` 实测：

```json
{"protectedCount":8,"keptDays":14,"maxProtected":200}
```

说明用户选择 14 天后，服务层读到了 14，配置链路是通的。

### 5.2 “剩余 N 天”显示错了

UI 写的是：

```js
'剩余 ' + row.keptDays + ' 天'
```

`row.keptDays` 是**总保留期**，不是剩余天数。  
一条 13 天前删除的记录，在 14 天保留期下仍然显示“剩余 14 天”。

修复：

- 后端返回 `expiresAt = at + keptDays * DAY`；
- 前端用 `expiresAt` 计算 `remaining = ceil((expiresAt - now)/DAY)`，最小 0；
- 显示“剩余 N 天”或“今天到期”，不要再显示总期。

### 5.3 到期清理只在启动时跑

`index.js` 目前只在 `ensureArchiveApi()` 时调用一次：

```js
void sweepExpiredTrash({ ..., ttlDays: readTrashKeptDays(config) })
```

运行中把保留期从 14 天改成 3 天，过期记录不会自动清，直到下次重启。

如果 UI 写“到期后自动彻底删除”，就必须：

- 定时 sweep（例如每小时，`unref()`，dispose 时取消）；或
- 打开回收箱/面板时触发一次 sweep；
- 每次 sweep 用当前 `readTrashKeptDays(config)`，不要用启动时的快照。

### 5.4 表单下拉缺少测试

`form.js` 新增了 `select`，但现有 `form.test.mjs` 只测 checkbox，没有测：

- 选择 14 天后，`mutate` 收到的 `path:['trashKeptDays']` 和数字值；
- 选择后配置订阅刷新，`select` 显示新值；
- 写入失败时回滚/提示。

需要补一条真实表单测试。
