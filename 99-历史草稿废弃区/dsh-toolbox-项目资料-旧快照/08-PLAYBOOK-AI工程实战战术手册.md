# PLAYBOOK.md

## AI 工程实战战术手册

> 来源：`dsh-toolbox` 从 S1 到 S6-a 的完整工程过程  
> 版本：1.0 ｜ 适用对象：技术负责人、架构师、AI 工程团队、独立开发者  
> 核心命题：**AI 能把代码写得很快；能把系统做对的，是验证系统。**

---

## 序言：这不是代码规范，是决策操作系统

大多数工程手册在教“怎么写代码”。  
这本手册教的是更前面、更后面的事：

- 先判断**哪里坏了**，再决定改哪里；
- 先设计**怎么证明修好了**，再写实现；
- 先定义**什么情况下必须停**，再谈进度；
- 先设计**怎么交接**，再谈发布。

`dsh-toolbox` 的经历很适合做样本：

- 6 个阶段；
- 448 项测试，0 跳过；
- 5 次封板审核；
- 多次被审查官打回；
- 最终留下的不是“没有 bug”的神话，而是一套**能被复用的判断顺序**。

这套顺序可以压成五句话：

1. **先证明会坏，再证明修好。**
2. **先查数据，再改代码。**
3. **一次只改一件事，改完立刻验证。**
4. **缺服务只降级，坏状态必须失败关闭。**
5. **做不到的如实说，代价算清楚。**

下面八章，是把这五句话展开成可执行的战术。

# 第一章 证据优先：先看见，再判断

## 1.1 事实分三层

工程争论里最常见的错误，是把“推断”说成“事实”。

| 层级 | 定义 | 例子 |
|---|---|---|
| **已确认** | 自己跑出来、能复现、有原始输出 | `workspace.json` 里仍有这条 id |
| **高可信推断** | 代码路径 + 现象吻合，但没有直接观测 | filtered getter 在目录移走后会藏行 |
| **未知** | 没查过，或环境不可见 | 用户浏览器里的旧缓存 |

审查官和 CTO 都必须要求团队把这三层分开写。  
“我觉得是缓存”不是结论；  
“我在 `workspace.json` 的 `tables.workspaces` 里看到了这条 id”才是证据。

## 1.2 证据阶梯

从强到弱：

```text
真实运行时状态 / 磁盘数据
  > 真实接口响应
  > 全量测试原始输出
  > 单条测试通过
  > 日志
  > 用户描述
  > 代码阅读推断
  > 直觉
```

注意：**日志也可能骗人**。  
如果日志只打印“cleanup 未完成: workspace”，没有 entity id、没有 error.message，它只证明“失败了”，不证明“为什么失败”。

## 1.3 案例：侧栏残留

S4 时出现“删除后左侧仍显示”的问题。团队先猜了三轮 UI 缓存，都没有解决。

最后有效的动作是：

1. 读 `workspace.json`；
2. 确认 `archivedSessionIds` 已清；
3. 确认 `tables.workspaces.*.sessionIds` 里仍有目标 id；
4. 读 `WorkspaceEntity.sessionIds`，发现它是 filtered getter；
5. 确认删除后目录不在原位，getter 不再返回目标行；
6. 确认 `dropWorkspaceRows` 用这个 getter 找行，所以永远找不到。

结论不是“刷新一下”，而是：**数据层有残留，UI 只是忠实显示。**

## 1.4 案例：验证工具假绿

同一时期，`verify-trash.mjs` 读的是：

```js
workspace.workspaces
```

真实结构是：

```js
workspace.tables.workspaces
```

于是“workspace 残留检查”永远拿到空数组，永远输出“没有残留”。  
这就是**假绿**：工具跑了、输出了、结论是错的。

规则：

> 任何一个“通过”的工具，都必须先证明它读的是正确的层级、正确的数据源、正确的语义。

## 1.5 证据优先检查表

- [ ] 我复现了吗？用的命令是什么？
- [ ] 我看的是磁盘、接口、运行时，还是二手描述？
- [ ] 这个工具/测试读的字段，和真实结构一致吗？
- [ ] 我能不能把“已确认/推断/未知”分开写？
- [ ] 如果结论错了，最可能错在哪一层？

# 第二章 分层审查：不要把四层问题混成一团

## 2.1 五层模型

一个插件/服务出问题，通常落在五层之一：

| 层 | 关注点 | 典型问题 |
|---|---|---|
| **契约层** | 官方 API、事件、服务形状 | `WebRoute.method` 被移除、`sessions.get` 语义变化 |
| **数据/状态层** | 状态机、journal、目录、锁 | 删除到一半、幽灵记录、死锁 |
| **传输/安全层** | 路由、token、Host、CORS、路径 | 伪造 Host、路径穿越、未授权删除 |
| **客户端/渲染层** | Session 列表、React、DOM、轮询 | 未分组闪现、订阅不到归档变化 |
| **交付/文档层** | 版本、tag、lock、索引、MANIFEST | 49+1=46、CRLF 清单、旧版本号 |

## 2.2 症状路由表

| 症状 | 先查哪层 | 常见根因 |
|---|---|---|
| 侧栏显示不对 | 数据/运行时 | 列表快照没刷新、workspace 行残留 |
| 操作报错 | 传输/契约 | 服务缺失、接口改名、token/路由 |
| 恢复后数据不对 | 数据/状态 | 快照丢了、状态机断层 |
| 显示“未命名” | 客户端/缓存 | 标题快照被删 |
| 终端反复刷屏 | 数据/状态 | 终态被当待办 |
| 资料库数字对不上 | 交付/文档 | 索引与事实脱节 |

## 2.3 案例：“未分组”不是实体

团队曾把“未分组”当成 workspace 里的一条记录去查，查不到，因为：

```text
未分组 = sessions.list − 各工作区成员
```

它不是实体，没有 `workspaceId`。  
所以：

- `dropWorkspaceRows` 对未分组返回“没有行可摘”是对的；
- 真正需要的是 `sessions.refresh()`；
- 在刷新完成前清归档标记，就会出现 <1 秒的未分组闪现。

**分层判断错了，修复就会打在错误的位置。**

## 2.4 审查顺序

```text
1. 复现并固定症状
2. 找到症状所属层
3. 只在这一层做最小修复
4. 验证修复没有把问题推到另一层
5. 补一条锁死该层的测试
```

## 2.5 CTO 视角

- 不要让一个团队同时改数据层和 UI 层；
- 每一层都要有 owner 和验收标准；
- 跨层修复必须有一次“联合验证”，不能各自宣布完成；
- 最重要的一条：**不要把“用户看到的现象”直接当根因。**

# 第三章 契约与适配：官方接口一定会变

## 3.1 为什么需要 adapter

平台升级时，最危险的不是“接口报错”，而是：

- 接口还在，但形状变了；
- 语义变了（`sessions.get` 从“在跑”变成“加载过”）；
- 属性读取本身会抛（未 inject 的服务）；
- 服务晚到；
- 返回值从 Promise 变成同步值，或反过来。

adapter 的职责不是“消灭变化”，而是：

> **把变化关在一个地方，让缺服务只降级，让必需服务明确失败。**

## 3.2 客户端 adapter 的最小设计

```js
const dsh = createDshAdapter(ctx)

const sessions = dsh.get('sessions')
if (!sessions) return              // 可选服务缺失 → 降级

const slots = dsh.require('slots') // 必需服务缺失 → 明确抛错
```

规则：

1. `get()` 缺服务/形状不对 → `undefined`，只警告一次；
2. `require()` 只对真正的入场券抛错；
3. `selfCheck()` 必须**每次真实探测**，不能在空环境返回 `ok:true`；
4. 调用方必须处理 `undefined`，不能拿到就点；
5. “必需”要按**功能作用域**定义，不是按整个插件定义。

## 3.3 案例：空环境 selfCheck 假绿

错误版本：

```js
const dsh = createDshAdapter({})
dsh.selfCheck()
// { ok: true, missing: [], available: [...] }   // 假绿
```

因为它只在 `get()` 时才填 `missing`。  
修正后：

```js
const dsh = createDshAdapter({})
dsh.selfCheck()
// { ok: false, missing: ['slots','sessions',...] }
```

**自检本身也必须被测试。**

## 3.4 宿主与客户端的差异

客户端：

- `slots` / `locale` 是入场券；
- `sessions` 对归档刷新很重要；
- `layout` / `configForms` 是可选能力。

宿主：

- `webServer` 缺失：只让 HTTP 归档接口不挂；
- `workspaceRegistry` 缺失：归档只读/关闭；
- `sessions` 缺失：判活失败关闭；
- `sessionQuery` 缺失：`session_search` 不注册。

关键：**不要让 `webServer` 缺失导致整个 host 插件不激活。**  
必需服务应该在功能入口 `require`，而不是在全局 `apply` 里一刀切。

## 3.5 适配层反模式

| 反模式 | 后果 |
|---|---|
| `const x = ctx.x` | 未 inject 时属性读取直接抛 |
| 缺服务返回空对象 | 调用方以为可用，后面才炸 |
| `selfCheck` 不探测 | 假绿，排障被带偏 |
| 所有服务都 `require` | 一个可选服务缺失，整个插件死 |
| 所有服务都 `get` 后不判空 | `undefined.foo` 崩溃 |
| adapter 只包一层就宣称“全收口” | 存量直接 `ctx` 仍在，契约一变仍白屏 |

## 3.6 契约检查表

- [ ] 这个服务是“入场券”还是“可选能力”？
- [ ] 缺了它，应该“少一个功能”还是“整个不工作”？
- [ ] 形状检查是否覆盖真正使用的方法？
- [ ] 自检是否真实探测？
- [ ] 晚到服务是否有 `ctx.inject` 等待？
- [ ] 失败分支是否能被单元测试模拟？

# 第四章 测试的可信度：绿灯不等于正确

## 4.1 红灯优先

顺序永远是：

```text
写一个会失败的测试
→ 确认它红在预期位置
→ 改代码
→ 看它变绿
→ 再补一条反向测试，证明旧实现确实会红
```

如果测试一开始就是绿的，先问：

- 它真的覆盖了新行为吗？
- 它是不是在断言一个永远为真的东西？
- 它是不是用了假的码、假的路径、假的 UI？

## 4.2 案例：假码测试

S4 的 reason 测试用了手写的 `'live'`，而真实服务返回 `'session-is-live'`。  
测试绿了，用户看到的仍是 `request-failed`。

修正方式不是“再加一个假码”，而是：

- 遍历服务层真实 `REASONS`；
- 用共享映射表；
- 测试映射表与服务层一致；
- 再加一条真实 HTTP/服务返回值测试。

**测试必须走生效路径。**

## 4.3 测试金字塔（插件版）

```text
                真机 / 浏览器
              端到端链路（E2E）
          契约/路由/状态机集成
        单元测试（纯逻辑、边界）
```

每一层解决不同问题：

- 单元：算法、匹配、状态迁移；
- 集成：真实 fs、journal、HTTP、service；
- E2E：真实链路、真实重启；
- 真机：用户能看到的行为、性能、缓存、渲染。

只有单元测试，不能证明插件在 DSH 里能活；  
只有真机测试，不能证明边界条件不会回归。**两层都要。**

## 4.4 0 skipped 的意义

“没装环境就 skip”很容易变成假绿。  
`dsh-toolbox` 最后把 Playwright 锁进 `devDependencies`，并明确：

- `npm ci` 装包；
- 浏览器二进制要单独 `npx playwright install chromium`；
- 没环境时报错，不 skip。

这不是为了追求数字，而是为了：

> **测试套件必须对“当前机器上到底验证了什么”诚实。**

## 4.5 测试反模式

| 反模式 | 问题 |
|---|---|
| 用假 id/假码/假路径 | 测的不是生产路径 |
| 只测 happy path | 失败关闭没验证 |
| 删断言让测试变绿 | 掩盖回归 |
| mock 掉所有依赖 | 真实形状变化测不到 |
| 依赖执行顺序 | 偶发绿/红 |
| 只跑新测试 | 旧契约被破坏不知道 |
| 用“测试全绿”代替真机 | 构建产物/缓存/时序仍可能坏 |

## 4.6 测试设计检查表

- [ ] 这条测试在修复前会红吗？
- [ ] 红在预期位置吗？
- [ ] 它调用的是生产同一份代码吗？
- [ ] 失败分支有覆盖吗？
- [ ] 真实数据形状/真实服务返回值覆盖了吗？
- [ ] 全量测试 0 skip 吗？
- [ ] 真机链路跑了吗？

# 第五章 状态机与可逆性：中间态才是事故现场

## 5.1 状态机先于代码

任何“删除/恢复/迁移/卸载”功能，先画状态机：

```text
Active → Archived → Trashed → Cleaned → Purged
          ↑            │
          └── 恢复 ─────┘
```

然后为每条边定义：

- 触发条件；
- 持久化记录；
- 失败时停在哪；
- 如何重试；
- 如何回滚/恢复；
- 用户看到什么。

## 5.2 四条不变量

以归档删除为例：

1. 同一会话不能同时出现在回收箱和侧栏；
2. 目录不存在时，不造新行；
3. purge 前必须 cleanup；
4. 恢复要回原位置。

**不变量比测试用例更重要。**  
测试可以漏， invariant 不能破。

## 5.3 锁与死锁

典型错误：

```js
withLock(id, async () => {
  await restore(id)   // restore 内部又 withLock(id) → 永久等待
})
```

修复：

```js
restoreLocked(id)    // 无锁实现
restore(id)          // 对外负责拿锁
```

规则：

- 锁不可重入时，必须拆出 `xxxLocked`；
- 内部调用只走无锁版本；
- 每条锁路径都要有超时/红灯测试；
- 测试不能只测“最终成功”，要测“不会挂起”。

## 5.4 持久化与幂等

删除不是“删文件”一个动作，而是一串：

```text
claim → move → cleanup → cleaned → purge
```

每一步都要：

- 落盘（journal）；
- 可重放；
- 幂等；
- 失败有 `lastError`；
- 重启能 heal。

没有持久化的状态机，只是一段乐观的函数调用。

## 5.5 可逆性：开关不是装饰

`reversible: true` 意味着：

- 关掉开关后，文本/样式/DOM/定时器/订阅全部恢复；
- 没有残留节点、没有重复 observer、没有覆盖新内容。

案例：汉化 `applied` 数组

旧方案：

```js
const applied = [] // 持有所有翻译过的节点
```

问题：

- React 替换节点 → 旧节点永久留在数组 → 内存泄漏；
- React 复用节点 → `restore()` 可能覆盖新文本；
- React 把同一节点改回英文 → 标记还在，不会重翻。

修正：

```js
Map<node, { original, translated }>
+ pruneApplied()       // 清 detached
+ isConnected 校验
+ nodeValue === translated 校验
+ 内容变化时当新原文重查
```

可逆不是“记得原文”这么简单，是**节点生命周期管理**。

## 5.6 状态机检查表

- [ ] 每条状态迁移都落盘了吗？
- [ ] 失败停在哪个状态？谁负责重试？
- [ ] 锁是否可重入？死锁测试有吗？
- [ ] 重放是否幂等？
- [ ] 目录不存在时会不会造幽灵？
- [ ] 每个副作用都能 dispose 吗？
- [ ] 关掉开关后 DOM/文本/定时器真的回去了吗？

# 第六章 失败关闭与安全：宁可拒绝，不造幽灵

## 6.1 失败关闭 vs 降级

不是所有失败都应该“继续跑”：

| 场景 | 正确策略 |
|---|---|
| 可选服务缺失 | 降级，少一个功能 |
| 必需服务缺失 | 明确失败，不半死不活 |
| 路径不安全 | 拒绝，不动文件 |
| journal 损坏 | 拒绝删除/清理，人工检查 |
| 活会话删除 | 拒绝 |
| token 缺失/错误 | 401，不执行 |
| 跨卷移动 | 拒绝，不做 copy+delete |

核心判据：

> **这个失败会不会造成不可逆的数据损坏？会，就失败关闭。**

## 6.2 路径安全

路径校验不是 `startsWith`：

```js
if (!realpathInside(root, candidate)) reject()
```

必须：

- `realpath` 解析；
- 拒绝 junction/symlink 逃逸；
- 拒绝 `..`；
- 目标末段/身份校验；
- 删除/恢复前再校验一次；
- 顶层链接拒绝。

## 6.3 传输安全

归档 HTTP 路由的安全模型：

- 只允许 loopback；
- Host 白名单来自真实监听地址，不信请求头；
- 同源检查；
- 拒绝 `X-Forwarded-*`；
- 每进程随机 token；
- 常量时间比较；
- 无 CORS；
- JSON + body 上限；
- 错误响应脱敏；
- 关闭开关即撤销路由 + 轮换 token。

**不要新增未认证的 `/debug`。**  
自检信息要么只写日志，要么复用同一套 token/Host/同源守卫。

## 6.4 日志与审计

- 日志记录**稳定码**，不记录路径/内容/token；
- 拒绝原因聚合，避免刷屏；
- 审计文件有上限/轮转；
- `lastError` 用于状态机诊断，不直接展示给最终用户；
- 面向用户的错误只给白名单文案。

## 6.5 不可逆动作的规矩

删除、物理清理、卸载、迁移：

1. 先备份；
2. 明确回滚路径；
3. 二次确认；
4. 失败关闭；
5. 记录审计；
6. 真机验证。

“先删了再说”不是勇敢，是事故。

# 第七章 真机与证据链：最后一公里最容易翻车

## 7.1 重启 ≠ 刷新

| 改动 | 生效方式 |
|---|---|
| `src/host/` | 重启 DSH |
| `src/client/` | Ctrl+F5 硬刷新 |
| 构建产物 `client.js` | 重新 build + 硬刷新 |
| 配置 | 看是否 live reload；不确定就重启 |

说错这一条，用户会白重启，团队会失去信任。

## 7.2 进程启动时间 vs 代码修改时间

真机排查先问：

```text
当前监听进程是什么时候启动的？
代码最后一次修改是什么时候？
```

如果代码 mtime 晚于进程启动时间，**当前进程根本没加载新代码**。  
“重启过了”不等于“加载了最新代码”。

## 7.3 构建产物

`client.js` 是构建产物，DSH 直接读它。  
改了 `src/client/` 不 build，真机跑的还是旧代码。

规则：

- 提交前 build；
- 有 `build-fresh` 测试就让它跑；
- 真机验证前确认产物时间/内容；
- 不把“源码改了”当“功能上线”。

## 7.4 证据包

每次真机验收至少留下：

1. commit / tag；
2. `npm test` 原始输出（0 skip）；
3. 工具输出（scan/contract/verify）；
4. 真机操作步骤 + 截图/录屏；
5. 已知限制；
6. 回滚方式。

没有证据包的“已验收”，只是口头承诺。

## 7.5 案例：2 秒轮询

归档状态在宿主 `workspaceRegistry`，不在客户端 session 列表。  
`session.list` 订阅监听不到归档变化，最后改成：

- 2 秒轮询；
- `visibilityState === 'hidden'` 暂停；
- `stop()` 清定时器；
- id 列表不变不重渲染。

三条规矩各有测试。  
这就是“真机行为”反推“客户端机制”的典型：不是猜，是验证。

## 7.6 真机检查表

- [ ] 进程启动时间 > 最后代码修改时间？
- [ ] 客户端改动 build + Ctrl+F5 了吗？
- [ ] 宿主改动重启了吗？
- [ ] 操作步骤能照抄吗？
- [ ] 基线数字有吗？
- [ ] 有截图/日志吗？
- [ ] 已知限制写了吗？

# 第八章 交接与归档：让下一个人能独立活着

## 8.1 一个事实只能有一个权威

文档、版本、配置、数据库 schema 都一样：

```text
一个事实 → 一处权威 → 其余全是引用
```

`dsh-toolbox` 的版本纪律：

- `package.json` 是版本源头；
- `package-lock.json` 必须同步；
- README / 索引 / 报告引用同一个版本；
- tag 指向最终 commit；
- 外部资料库是只读备份，不是第二权威。

## 8.2 文档与备份

推荐关系：

```text
仓库 docs/              = 唯一权威，随代码提交
外部项目资料库           = 只读快照 + MANIFEST
```

规则：

- 修改先改仓库 docs；
- 外部资料库不手工编辑；
- 每次快照重新生成 MANIFEST（LF 行尾）；
- 时间戳评审报告不改名；
- 备份用 hash 检测漂移。

## 8.3 版本与 tag

发版前：

- [ ] `package.json` / `package-lock.json` 版本一致；
- [ ] README / 索引 / 报告版本一致；
- [ ] 448+ 测试全绿，0 skip；
- [ ] 工具链通过；
- [ ] git status 干净；
- [ ] tag 指向最终 commit；
- [ ] 资料库数字和事实一致；
- [ ] MANIFEST 校验通过。

**不要在数字不一致的文档上打 tag。**  
tag 是承诺，不是装饰。

## 8.4 已知限制要写下来

不是所有缺陷都要修。  
但所有“不修”的决定都要记录：

- 现象；
- 根因；
- 为什么不修；
- 代价；
- 何时重新评估。

`dsh-toolbox` 的例子：

- <1 秒未分组闪现：数据正确，不做两阶段删除；
- `slots`/`locale` 25 处豁免：必需入场券，缺失即明确失败；
- `sessionQuery` 专用 `serviceOf` 豁免：S4 已验证晚到场景。

**“已知限制”不是“待修 bug”，但没有记录的“已知限制”就是隐患。**

## 8.5 交接包

一个可交接项目至少包含：

1. 一页当前状态；
2. 运行/构建/测试命令；
3. 架构图和关键数据流；
4. 已知限制与豁免清单；
5. 发版/回滚手册；
6. 证据目录；
7. 下一个接手人的前三步。

## 8.6 交接检查表

- [ ] 新人能按 README 跑起来吗？
- [ ] 测试 0 skip 吗？
- [ ] 版本/tag/lock 一致吗？
- [ ] 文档有唯一权威吗？
- [ ] 备份有 MANIFEST 吗？
- [ ] 已知限制写了吗？
- [ ] 回滚路径明确吗？
- [ ] 下一个人知道先看哪三份文档吗？

# 附录 A：审查官协议

## A.1 分级

| 级别 | 定义 | 处理 |
|---|---|---|
| P0 | 数据损坏/安全/死锁/不可启动 | 立即停线，修复后重审 |
| P1 | 功能错误/状态不一致/可复现残留 | 封板前必修 |
| P2 | 体验/文档/可维护性 | 可排期 |
| P3 | 文案/命名/小瑕疵 | 顺手修 |

## A.2 每条意见必须带

```markdown
| # | 问题 | 证据 | 修法 | 验收 |
```

没有证据的意见是猜测；没有验收的修法是空话。

## A.3 审查顺序

```text
数据/状态 → 传输/安全 → 客户端/渲染 → 文档/发布
```

先修会导致数据损坏的，再修体验。

# 附录 D：反模式清单

1. 用 `replace` 改代码不验证，静默没改。
2. 改了源码忘了 build。
3. 让用户白重启：进程启动时间早于代码修改时间。
4. 用“测试绿了”代替真机。
5. 一次改多处，出问题不知道是哪处。
6. 猜根因，不查磁盘/运行时。
7. 为了消噪音跳过必要重试，把待办当终态。
8. 为 <1 秒视觉问题引入新接口/新中间态。
9. 用假 id/假码/假路径写测试。
10. 删断言让测试变绿。
11. 未认证 `/debug` 端点。
12. 文档和代码各说一个版本。
13. 把“已知限制”当“待修 bug”，或反过来把 bug 藏进“限制”。
14. 用 `startsWith` 代替 `realpath`。
15. 用数组永久持有 DOM 节点。
16. 在锁内调用带锁函数。
17. 删除前不备份，失败后无回滚。
18. 外部备份可编辑，形成第二权威。

# 附录 E：CTO 的 30 天训练计划

## 第 1 周：证据

- 每天挑一个 bug，只写“已确认/推断/未知”；
- 禁止在没有原始输出的情况下下结论；
- 练习用磁盘/接口/运行时三选二取证。

## 第 2 周：分层

- 每个事故先归类到五层；
- 让不同人负责不同层；
- 复盘“修错层”的案例。

## 第 3 周：测试

- 每个修复必须先写红灯；
- 检查测试是否走生产路径；
- 做一次“删掉实现，测试必须红”的演练。

## 第 4 周：发布与交接

- 做一次完整发版清单；
- 做一次回滚演练；
- 让另一个人只靠文档接手一个小功能。

# 结语

AI 工程的最大风险，不是“AI 不会写代码”。  
是团队把“AI 写得很快”误当成“系统已经正确”。

真正稀缺的能力是：

- 知道该看哪里；
- 知道什么算证据；
- 知道什么时候必须停；
- 知道怎么证明修好了；
- 知道怎么让下一个人接手。

这五件事，测试替不了，文档替不了，模型也替不了。  
它们是工程负责人的工作。

> **先证明会坏，再证明修好。**  
> **先查数据，再改代码。**  
> **一次只改一件事，改完立刻验证。**  
> **缺服务只降级，坏状态必须失败关闭。**  
> **做不到的如实说，代价算清楚。**

这五句话，就是这本 PLAYBOOK 的全部。
