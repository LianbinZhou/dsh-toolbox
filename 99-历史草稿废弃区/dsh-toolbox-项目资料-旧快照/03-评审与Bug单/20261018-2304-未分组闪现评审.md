# 未分组闪现评审：解释正确，但不建议为它临时加接口

> 现象：删除 → 入回收箱的一瞬间，左侧「未分组」闪现同一条会话，不到 1 秒后消失。
> 复核时间：2026-10-18
> 审核角色：审核官（只读）

---

## 0. 结论

Harness 对成因的解释是对的：

```text
1. 目录移入回收箱
2. 清掉 archivedSessionIds
3. HTTP 返回
4. 客户端 sessions.refresh()
```

在 2 和 4 之间，DSH 认为这条会话「已取消归档、但仍在 Session 列表里」，于是按规则把它归入「未分组」。  
`refresh` 完成后目录已不在，它才从列表消失。

这是**排序窗口**，不是数据错误：

- 回收箱有记录；
- 目录在 trash；
- journal phase 正确；
- 归档标记已清；
- 刷新后列表正确。

我同意 Harness 的初步判断：**不值得为了不到 1 秒的闪现，在 S4 封板前临时加一条新路由和两次往返。**

但我不建议把它说成“彻底修复”；它是**已知的 cosmetic 边界**，应记录在 S4 简报/README，留到 S5 或专门一轮做两阶段删除。

---

## 1. 两阶段方案是否技术正确？

技术上是正确的：

```text
1. delete：只移目录，不清归档标记，返回 cleanupRequired
2. 客户端 sessions.refresh()
3. cleanup：清归档标记/workspace 行/缓存
```

为什么这样不闪：

- 第 1 步后会话仍然在归档集合里，侧栏隐藏；
- 第 2 步刷新时目录已经没了，Session 列表直接把它移除；
- 第 3 步清标记时，它已经不在 Session 列表里，不会再被归入未分组。

如果第 2 步失败，就不做第 3 步：会话继续隐藏，回收箱仍有记录，用户可重试。  
如果第 3 步失败：会话仍归档隐藏，回收箱有记录，`phase` 保持 `trashed`，可重试。  
这个失败语义比“先清标记再刷新”更安全。

---

## 2. 但这个改动并不只是“多一个路由”

它引入一个新的两阶段状态，必须同时处理：

1. `/cleanup` 必须复用现有 token / Host / 同源守卫；
2. 只允许清理 `trashed` 状态的记录，不能清 `deleting`；
3. 必须幂等：重复 cleanup、cleanup 与 restore 并发、cleanup 与 purge 并发都要有稳定结果；
4. 第一次 delete 后、cleanup 前，归档面板不能提前刷新出“仍在归档”的行；
5. 如果 `sessions.refresh()` 失败，不能继续 cleanup；
6. 第二次调用失败时，UI 要告诉用户“文件已在回收箱，但标记未清”，而不是显示普通删除失败；
7. 需要新增 E2E：
   - 刷新成功 → cleanup → 无闪现；
   - 刷新失败 → 不 cleanup，侧栏隐藏，回收箱在；
   - cleanup 失败 → 可重试；
   - restore 插在 refresh 与 cleanup 之间 → 不误删标记/不误 detach。

这不是不能做，而是**不能把它当成一个顺手补丁**。S4 已经因为“看起来很小的改动”踩过多次坑；如果现在做，必须按一个小特性来验收。

---

## 3. 我的建议

### 对 S4

**接受这个 <1 秒闪现，记录为已知 cosmetic 问题，不阻断 S4 封板。**

理由：

- 数据 100% 正确；
- 没有残留，刷新后一致；
- 不到 1 秒，且不可稳定截图；
- 新增两阶段接口会把 S4 的失败面重新扩大；
- 当前更值得做的是把 S4 的证据和文档收干净，而不是再引入一条状态机分支。

### 对 S5 或专门一轮

如果这个观感必须消掉，按下面顺序做：

1. 先写失败测试：refresh 延迟、refresh 失败、cleanup 失败、restore 插队；
2. 再加 `deferCleanup` / `/cleanup`；
3. UI 严格按 `delete → sessions.refresh → cleanup → panel.refresh` 顺序；
4. 真机录屏或 DevTools Performance 确认没有未分组帧；
5. 再合并。

不要用 `setTimeout` 延迟清标记，也不要用 CSS/本地隐藏去遮——那只是把窗口变成不确定。

## 4. `verify-trash.mjs` 要跑吗？

**要跑，但它抓不到这个闪现。**

它读的是磁盘和接口的最终状态：

- 回收箱记录；
- workspace 成员；
- projection cache；
- 归档集合。

闪现发生在客户端 Session 列表刷新之前，脚本运行时通常已经刷新完，所以它会显示“无残留”。  
它的价值是证明**最终态正确**，不是证明中间没有渲染窗口。

建议：

```bash
node tools/verify-trash.mjs
```

在最后一次真机链路之后、以及重启后再各跑一次，把输出留档。  
闪现本身要靠浏览器 Performance/录屏，或在 `delete` 返回与 `sessions.refresh()` 完成处打时间戳来证明。
