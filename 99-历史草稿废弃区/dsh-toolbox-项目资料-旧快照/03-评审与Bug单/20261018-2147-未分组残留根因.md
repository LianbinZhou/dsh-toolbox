# 未分组会话删除后仍在侧栏：根因与修复方案

> 针对会话：`session-42c318e7-71df-4b5d-bbcd-a4a4a8b7f8ee`
> 场景：未分组 → 归档 → 历史归档 → 删除 → 入回收箱
> 现象：回收箱有它，左侧「未分组」也还有它
> 复核时间：2026-10-18
> 审核角色：审核官（只读）

---

## 0. 结论

**这次不是 workspace 行残留，也不是回收箱状态不对。**

这条会话已经满足：

```text
archivedSessionIds 不包含它
journal phase = cleaned
回收箱有它的 trash 目录
sessions 目录已经没有它
所有 workspace 的 sessionIds 都不包含它（它是未分组）
```

所以「左侧未分组」这一行不是 workspace 成员，也不是归档集合。

它来自 **DSH 客户端的 Session 列表（`ctx.sessions.list`）**。  
插件删除文件后只刷新了「历史归档」自己的列表，**没有让 DSH 的 Session 列表重新拉取**。

**一句话：未分组会话根本不走 `dropWorkspaceRows`，它需要的是 `ctx.sessions.refresh()`。**

因此「未分组还有一行」只能是 **客户端 Session 列表还没重新拉取**。

## 2. 为什么之前的 workspace 修复碰不到它

当前 `dropWorkspaceRows` 对未分组有一段：

```js
if (dropped === 0 && !already && targetWorkspace === null) {
  return { ok: true, dropped: 0, already: true, reason: 'ungrouped' }
}
```

这段逻辑本身是对的：

- 未分组会话本来就不在 workspace 的 `sessionIds` 里；
- 没有行可摘；
- 不应该把删除卡在 `trashed`。

但它只解决了「不要误判失败」，**没有解决侧栏那一行**。

DSH 的「未分组」不是从 workspace 表算出来的，而是：

```text
sessions.list
  → list.ids / list.byId
  → 减去所有 workspace.sessionIds
  → 剩下的就是未分组
```

删除文件后，`sessions.list` 里仍然是删除前的快照；  
archive panel 只调用了自己的 `panel.refresh()`，没有调用 DSH 的 `sessions.refresh()`。

所以：

```text
磁盘：目录没了
归档：标记没了
回收箱：有记录
Session 列表：还是旧快照 → 未分组继续显示
```

## 3. DSH 侧可用的刷新入口

`dsh-api-session-controller` 的客户端 `ClientSessions` 暴露了公开方法：

```js
refresh() {
  return this.manager.refreshList()
}
```

即：

```js
ctx.sessions.refresh()
```

它会重新拉取 `session/list`，重建 `sessions.list` 快照。  
官方 `dsh-client-ui-input-trigger` 等插件也是通过 `sessions` 服务取会话列表的。

当前 `dsh-toolbox` 的客户端入口只注入：

```js
inject: ['slots', 'locale']
```

没有注入 `sessions`，archive panel 也没有在任何删除/恢复/彻底删除之后调用 `sessions.refresh()`。

---

## 4. 修复方案

### 4.1 注入 sessions

客户端入口：

```js
return {
  inject: ['slots', 'locale', 'sessions'],
  apply,
}
```

如果担心某些 profile 没有 sessions，可改用 `ctx.inject(['sessions'], cb)`，但 DSH 的 web profile 一定有；直接把 `sessions` 加进 inject 更简单。

### 4.2 删除/恢复/彻底删除后刷新 Session 列表

在 `archive-panel.js` 的 `run` 包装里，动作完成后调用：

```js
async function refreshHostSessions() {
  try {
    const sessions = ctx.sessions ?? ctx.get?.('sessions')
    if (sessions && typeof sessions.refresh === 'function') {
      await sessions.refresh()
    }
  } catch (error) {
    console.warn('[dsh-toolbox] sessions.refresh failed after archive action', error)
  }
}

const run = (action) => async () => {
  setBusy(true)
  try {
    await action()
    await refreshHostSessions()
  } finally {
    sync()
    setBusy(false)
  }
}
```

需要覆盖的动作：

- 删除 → 入回收箱；
- 回收箱恢复；
- 回收箱彻底删除；
- 历史归档页「恢复」（unarchive）。

### 4.3 不把未分组当失败

保留现有的：

```js
reason: 'ungrouped'
```

它是正确的：未分组没有 workspace 行可摘，不能因此把 phase 停在 `trashed`。  
真正要做的是 **刷新 Session 列表**，不是给未分组造一行 workspace。

### 4.4 `scrubCache` 仍要检查

我观察到这条会话的 per-session `session_projcache` 文件还在：

```text
~/.dsh/storages/session_projcache/sessions/session-42c318e7....json
```

它不一定直接决定未分组列表，但说明 `scrubCache` 在这条路径上没有真正删掉文件（可能是 Windows 文件被占用，`unlinkSync` 失败被吞）。

建议：

- `scrubCache` 返回 `{ ok, touched, failed }`，失败时写日志/`lastError`；
- Windows 上遇到 `EBUSY/EPERM` 时重试，或改用“重命名后删除”；
- 不要把 `unlink` 失败继续当成功。

### 4.5 测试

新增一条真正的 UI 回归：

- fake `sessions.refresh` 计数；
- 点击「删除 → 入回收箱」后，`sessions.refresh` 必须被调用；
- 点击回收箱「恢复」/「彻底删除」后也必须调用；
- `makeCtx` 里提供 `sessions` 服务，render 测试不再只测 model。

再加一条真机验收：

1. 未分组会话 → 归档 → 历史归档 → 删除 → 入回收箱；
2. 左侧未分组行立即消失，回收箱仍有；
3. 不重启、不硬刷新也成立；
4. 恢复后回到未分组；
5. 彻底删除后回收箱和 Session 列表都没有。

## 5. 为什么不要选 A / B

- A（保持现状）：未分组残影会一直存在，用户必须重启/硬刷新；
- B（删除时不清归档标记）：未分组照样在 Session 列表里，且归档集合会指向一个已不在磁盘的会话；
- 真正的问题在 **Session 列表客户端快照**，不是归档标记，也不是 workspace 行。

选 A/B 都不是修复。

## 6. 需要 Harness 立刻验证的诊断

在删除前后分别执行：

```js
ctx.sessions.list.getSnapshot()
```

看 `list.byId` 里还有没有目标 id。

- 删除后仍有：证明是 Session 列表快照未刷新；
- 删除后没有、侧栏仍有：才是渲染层缓存，另查 UI；
- 如果删除前 `sessions.get(id)` 仍存在（live），删除本应被拒绝，需要查 live 判断。

这比继续在 workspace 行上试错更快。

---

## 7. 一句话

> 未分组会话没有 workspace 行可摘；`dropWorkspaceRows` 返回 `ungrouped` 是对的。  
> 但删除后没有调用 `ctx.sessions.refresh()`，DSH 的 Session 列表仍是旧快照，所以「未分组」和回收箱同时显示。  
> 补上 sessions 注入 + 动作后 refresh，才是这条链路的真正修复。
